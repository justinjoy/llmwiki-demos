## 1. payment/pay 개체 정의 및 병합 검토

### 반례
단순히 명칭에 동일한 문자열('pay' / 'payment')이 포함되어 있다는 이름의 유사성에만 의존하여, 결제 도메인 개념 및 식별자 속성인 `payment`를 결제 서비스 개체인 `pay`(`Service`)와 동일한 개체로 단정하고 자동 병합하는 케이스.

### 현재 모델 점검
- [raw/ARCH-01_v1.md](raw/ARCH-01_v1.md) 1절 및 `types.csv`에서 `pay`는 결제 기능을 수행하는 실제 서비스 개체(`Service`, `svc:pay`)로 명시되어 있습니다.
- `payment`는 API 경로(`/v1/payments/authorize`)나 결제 건 식별자(`payment_id`) 등 도메인 속성 및 경로 표현으로 사용되고 있습니다.
- 용어 사전 문서인 `GLOSS-01`은 이번 입력 데이터에 포함되어 있지 않으므로, 이를 읽었다고 인용하거나 분석 근거로 사용할 수 없습니다.

### 유지 또는 수정 제안
- **유지 제안**: `types.csv`의 `Service` 개체로 `pay`를 계속 유지하고, `payment` 개념을 `pay` 서비스로 자동 병합하지 않습니다. 병합 여부는 '확인 보류'로 기록합니다.
- **수정 대상 파일**: 없음 (`types.csv`, `relations.csv`, `questions.csv` 현행 유지)

### 근거
[raw/ARCH-01_v1.md](raw/ARCH-01_v1.md) 1절 및 2절에서 `pay`는 독립적인 결제 서비스로 기술되어 있으며, `payments`는 API 경로의 명사형 표현 및 `payment_id` 속성명으로 사용됩니다. `GLOSS-01` 문서는 현재 미입력 상태이므로 용어 정의에 기초한 개체 병합을 수행할 수 없습니다.

### 남은 확인
입력되지 않은 문서인 `GLOSS-01`을 후속 단계에서 확보한 후, 결제 도메인 용어 정의 및 개체 간 관계를 재검토하여 `payment`와 `pay` 간의 병합 여부를 최종 확정해야 합니다.

## 3. ledger/ledger-db 개체 타입 구분 점검

### 반례
`ledger-db`라는 명칭에 'ledger'가 포함되어 있다는 이유만으로, 저장소 개체인 `ledger-db`를 서비스 개체인 `ledger`(`Service`)와 동일 개체로 병합하거나 개체 타입을 구분하지 않고 단일 개체로 처리하는 케이스.

### 현재 모델 점검
- `ledger`는 API(`POST /v1/journal-entries`)를 제공하고 결제정산팀이 운영을 담당하는 서비스 개체(`Service`)입니다.
- `ledger-db`는 [raw/INC-03_v1.md](raw/INC-03_v1.md) 장애 보고서에서 DB 연결 대기 및 데이터 잠금 현상이 발생한 물리적 데이터 저장소(`DataStore` 후보 타입)입니다.
- `types.csv`에 `DataStore` 타입이 `ledger-db(존재·타입·소유 서비스 확인 보류)`로 독립 기재되어 있으며, `relations.csv`에서는 DB 접속 관계를 `depends_on` 직접 의존 관계에서 제외하도록 명시하고 있습니다.

### 유지 또는 수정 제안
- **유지 제안**: `Service`(`ledger`)와 `DataStore`(`ledger-db`)를 서로 다른 개체 타입으로 명확히 구분하는 현행 모델을 유지하며, DB 이름만으로 동일한 `Service`로 병합하지 않습니다.
- **수정 대상 파일**: 없음 (`types.csv`, `relations.csv`, `questions.csv` 현행 유지)

### 근거
[raw/ARCH-01_v1.md](raw/ARCH-01_v1.md) 2절·3절에서 `ledger`는 HTTP 동기 요청을 수신하는 서비스(`Service`)로 정의되어 있으며, [raw/INC-03_v1.md](raw/INC-03_v1.md) 3절·4절에서 원장 DB(`ledger-db`)는 데이터 잠금 및 DB 연결 풀 소진의 대상이 되는 데이터 저장소로 기술되어 있어 두 개체의 역할과 타입이 명확히 구분됩니다.

### 남은 확인
`ledger-db`에 대한 세부 아키텍처 정보(소유 서비스, 물리 인프라 구성 등)가 포함된 원문 자료를 추가 확보하여 `DataStore` 개체 타입 및 속성을 확정해야 합니다.

## 4. API와 서비스 호출 관계 및 운영 팀 구별

### 반례
- 서비스 간 호출 관계를 모델링할 때 호출 방향을 반대로 처리하거나(`API`가 `Service`를 호출함), 간접 호출 경로(`shop` → `ledger`)를 직접 의존 관계(`depends_on`)로 잘못 포함시키는 케이스.
- API 제공 서비스(`Service`)와 해당 서비스를 담당하는 운영 조직(`Team`)을 혼동하여, API의 제공 주체를 서비스가 아닌 운영 팀으로 연결하는 케이스.

### 현재 모델 점검
- 호출 관계 체계는 `calls_api`(호출 서비스 → API)와 `api_of`(API → 제공 서비스)의 결합을 통해 서비스 간 직접 호출 관계인 `depends_on`(호출 서비스 → 제공 서비스)으로 투영됩니다.
- 운영 책임을 나타내는 `owned_by` 관계(`Service` → `Team`)를 별도로 운영하여 API 제공 서비스와 운영 담당 팀을 엄격하게 구별하고 있습니다.

### 유지 또는 수정 제안
- **유지 제안**: 현행 `calls_api`, `api_of`, `depends_on`, `owned_by` 관계 정의 및 투영 구조를 그대로 유지합니다.
- **원문 API 투영 예시 설명**:
  1. **쇼핑몰 → 주문**: `shop` `calls_api` `api:order:POST /v1/orders` (`api_of` `order`) ⇒ `depends_on`: `shop` → `order` (운영 책임: `order` `owned_by` `커머스플랫폼팀`)
  2. **주문 → 결제**: `order` `calls_api` `api:pay:POST /v1/payments/authorize` (`api_of` `pay`) ⇒ `depends_on`: `order` → `pay` (운영 책임: `pay` `owned_by` `결제정산팀`)
  3. **결제 → 원장**: `pay` `calls_api` `api:ledger:POST /v1/journal-entries` (`api_of` `ledger`) ⇒ `depends_on`: `pay` → `ledger` (운영 책임: `ledger` `owned_by` `결제정산팀`)
- **수정 대상 파일**: 없음 (`types.csv`, `relations.csv`, `questions.csv` 현행 유지)

### 근거
[raw/ARCH-01_v1.md](raw/ARCH-01_v1.md) 1절 및 2절의 호출 구간별 API 정의/타임아웃 표, 3절의 서비스별 운영 담당 팀 구별(쇼핑몰·주문 서비스는 커머스플랫폼팀, 결제·원장 서비스는 결제정산팀).

### 남은 확인
향후 [raw/ARCH-01_v2.md](raw/ARCH-01_v2.md) 비동기 전환안이 확정되어 운영에 적용될 경우, HTTP API 호출 관계 외에 메시지 이벤트 발행/구독 관계(예: `publishes_event`, `subscribes_event`)를 온톨로지 관계 모델에 추가하는 방안을 검토해야 합니다.

## 5. 운영 조건 및 동적 상태 관리

### 반례
문서에 명시된 정적 운영 조직(`Team`) 관계 외에, 실시간으로 변동되는 당직자 개인 정보, 특정 장애 시점의 지표 수치, 일시적인 작업 중지/재개 승인 상태 등을 온톨로지의 정적 `owned_by` 관계나 서비스 개체 속성으로 오인하여 모델링하는 케이스.

### 현재 모델 점검
- `types.csv` 및 `relations.csv`는 서비스와 운영 담당 팀 간의 정적 정합성(`shop`/`order` → `커머스플랫폼팀`, `pay`/`ledger` → `결제정산팀`)만을 정적 관계(`owned_by`)로 관리합니다.
- `questions.csv` (2번 및 3번 질문)에서는 현재 당직자, 장애 시점의 지표, 대사 큐 중지 실행 승인 조치 등을 정적 관계 모델과 분리하여 '확인 보류' 및 '별도 당직표/미제공 원문 확인 필요 사항'으로 올바르게 구분하고 있습니다.

### 유지 또는 수정 제안
- **유지 제안**: 서비스 운영 담당 팀(`owned_by`) 관계는 정적 온톨로지로 계속 관리하고, 실시간 당직자, 동적 지표, 실행 승인 여부는 정적 온톨로지 관계에서 제외하고 '확인 보류' 상태로 구분 유지합니다.
- **수정 대상 파일**: 없음 (`types.csv`, `relations.csv`, `questions.csv` 현행 유지)

### 근거
- **담당 팀 vs 당직자**: [raw/ARCH-01_v1.md](raw/ARCH-01_v1.md) 3절에서 운영 담당 팀(커머스플랫폼팀, 결제정산팀)은 정적으로 명시된 반면, "당직자와 연락처는 당직표에서 확인"으로 기재되어 개인 당직자는 실시간 변동 대상임을 나타냅니다.
- **현재 지표**: [raw/INC-03_v1.md](raw/INC-03_v1.md) 1절 및 3절의 p95 지연 및 처리 건수는 2026-08-18 장애 발생 당시의 과거 시점 측정 지표입니다.
- **실행 승인**: [raw/ADR-07_v1.md](raw/ADR-07_v1.md) 3절 및 [raw/INC-03_v1.md](raw/INC-03_v1.md) 4절에서 대사 큐 중지·재개 절차는 미제공 문서인 `OPS-04 v1`에 의존하고 있어 현재 실행 승인 조건을 확정할 수 없습니다.

### 남은 확인
미제공 문서인 `RUN-02 v1` 및 `OPS-04 v1`을 수령하여 대사 큐 제어 절차와 알림 운영 기준을 확인하고, 실시간 당직표 시스템 및 모니터링 시스템과의 정적 온톨로지 연동 구조를 설계해야 합니다.
