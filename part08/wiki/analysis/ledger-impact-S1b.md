## 1. 전파 경로 및 후보별 사실 ID 경로

원장(`ledger`) 저장 지연 발생 시 서비스 간 도달 가능성(reachability)에 따른 점검 대상 후보는 `notify`, `order`, `pay`, `shop`이며, 이는 전파 가능성에 따른 점검 대상일 뿐 실제 장애 확정과 다릅니다.

미결제 주문이 출고되는 문제를 방지하기 위해 주문 서비스(`order`)가 결제 서비스(`pay`)를 동기로 호출하여 승인을 확인한 뒤 주문을 확정하므로, 원장(`ledger`) 지연 시 결제 및 주문 확정이 지연될 수 있습니다 ([ADR-07 v1 §1](../../raw/ADR-07_v1.md), [ADR-07 v1 §2](../../raw/ADR-07_v1.md), [ARCH-01 v1 §2](../../raw/ARCH-01_v1.md)).

S1b 스냅샷 및 `candidate-v1` 규칙에 따른 후보별 경로 및 사실 ID(Assertion ID) 경로는 다음과 같습니다:

| 후보 서비스 | 대상 서비스 | 호출 경로 (Services) | 사실 ID 경로 (Assertion IDs) | 서비스 링크 |
| --- | --- | --- | --- | --- |
| `notify` | `ledger` | `notify` → `order` → `pay` → `ledger` | F04 → F02 → F03 | - |
| `order` | `ledger` | `order` → `pay` → `ledger` | F02 → F03 | [order](../services/order.md) |
| `pay` | `ledger` | `pay` → `ledger` | F03 | [pay](../services/pay.md) |
| `shop` | `ledger` | `shop` → `order` → `pay` → `ledger` | F01 → F02 → F03 | - |

## 2. notify 알림 지연의 의미

- **처리 흐름**: 알림 워커(`notify`)는 고객경험플랫폼팀이 운영하며, 주문 완료 이벤트를 수신하면 주문 서비스(`order`)의 상태 조회 API(`GET /v1/orders/{order_id}/status`)를 호출하여 주문 확정(`CONFIRMED`) 상태임을 확인한 뒤 알림을 발송합니다 ([RUN-02 v1 §1](../../raw/RUN-02_v1.md), [RUN-02 v1 §3](../../raw/RUN-02_v1.md)).
- **지연 시 대응 및 격리 조건**:
  - 상태 조회 타임아웃 시 알림 발송을 보류하고 재시도 간격을 점차 늘립니다 ([RUN-02 v1 §2](../../raw/RUN-02_v1.md)).
  - 알림 처리 오류로 인해 주문 상태를 변경하거나 결제를 취소하지 않습니다 ([RUN-02 v1 §2](../../raw/RUN-02_v1.md)).
- **과잉 해석 교정**: `notify` 장애/지연은 결제 실패를 의미하는 것이 아니며, 알림 처리 오류가 주문 상태 변경이나 결제 취소로 이어지지 않도록 처리합니다.

## 3. 과거 관측 기록 (186/4,900건 · 25분 · 42분)의 의미

과거 장애 보고서([INC-03 v1](../../raw/INC-03_v1.md))의 수치에 대한 상세 의미는 다음과 같습니다:

- **186 / 4,900건**: 2026년 8월 18일 장애 당시 발생한 카드 결제 주문 4,900건 중 186건의 주문 확정이 지연된 관측치입니다 ([INC-03 v1 §1](../../raw/INC-03_v1.md)). 이는 승인 실패나 전체 주문 중단이 아닌 주문 확정 지연 건수입니다.
- **25분**: 신규 주문의 처리 지연이 지속된 시간(09:42~10:07)입니다 ([INC-03 v1 §3](../../raw/INC-03_v1.md)).
- **42분**: 최초 경보 시각(09:42)부터 지연 주문 186건의 대사 완료까지 걸린 소요 시간(10:24 마침)입니다 ([INC-03 v1 §3](../../raw/INC-03_v1.md)).
- **주의사항**: 위 수치들은 과거 장애 사례(INC-03)에서의 관측 기록일 뿐이며, 향후 복구 시간이나 영향을 보장하는 기준이 아닙니다.

## 4. OPS-04 대사 작업 중지 조건 · 범위 · 승인

원장 장애 시 대사 작업 중지 및 재개 절차([OPS-04 v1](../../raw/OPS-04_v1.md)) 기준은 다음과 같습니다:

- **진입 조건**:
  1. 원장 저장 타임아웃이 **5분 이상** 지속될 것 ([OPS-04 v1 §1](../../raw/OPS-04_v1.md)).
  2. PG 승인 내역과 원장 기록의 **불일치가 확인**될 것 ([OPS-04 v1 §1](../../raw/OPS-04_v1.md)).
- **실행 승인**:
  - **결제정산팀 당직자**와 **장애 대응 책임자**의 사전 승인을 받은 후 작업합니다 ([OPS-04 v1 §1](../../raw/OPS-04_v1.md)).
- **조치 범위**:
  - 승인받은 대상 가맹점(`merchant_id`)의 **결제 대사 큐 소비만 일시 중지**합니다 ([OPS-04 v1 §2](../../raw/OPS-04_v1.md)).
  - **PG 승인 API** 및 **다른 가맹점의 대사 작업**은 정상 운영을 유지합니다 ([OPS-04 v1 §2](../../raw/OPS-04_v1.md)).
- **과잉 해석 교정**: 즉시 전체 결제를 중단하는 것이 아니며, 5분 이상 타임아웃 및 불일치 확인 후 승인을 받아 영향 가맹점의 대사 큐만 국소적으로 중지합니다.

## 5. [제안] 장애 대응 제안

- **[제안]**: 장애 대응 시 커머스플랫폼팀 및 결제정산팀과 협조하여 큐 대기 건수와 상태 조회 오류를 우선 점검하고, 규정된 승인 절차에 따라 대사 큐 중지 범위를 제어할 것을 제안합니다 ([ARCH-01 v1 §3](../../raw/ARCH-01_v1.md), [RUN-02 v1 §3](../../raw/RUN-02_v1.md)).
