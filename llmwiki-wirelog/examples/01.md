# ledger가 지연되면 어떤 서비스를 점검해야 하고, notify의 결제 취소로 이어지는가?

기준: S1b · PyreWire 1.1.2 · 교육용 자료

- **사실** S1b 스냅샷 기준 ledger 지연 발생 시 상류(upstream) 호출 경로에 따라 점검해야 하는 대상 서비스 후보는 pay, order, shop, notify이다. [E1]
- **사실** 상류 그래프 경로 상 pay는 ledger를 직접 동기 호출하고(F03), order는 pay를 호출하며(F02), shop과 notify는 order에 의존한다(F01, F04). [E1]
- **사실** 그래프 호출 경로는 도달 가능성에 따른 점검 대상 후보일 뿐이며, 실제 장애 확정이나 장애 전파를 보장하는 것은 아니다. [E1]
- **사실** 결제 서비스(pay)는 원장 서비스(ledger) 호출 타임아웃(1.8초) 발생 시에도 결제를 취소하지 않고 '원장 반영 대기(LEDGER_PENDING)'로 저장한 뒤 대사 큐에 등록한다. [E8] [E11]
- **사실** 주문 서비스(order)는 결제 응답이 지연되면 주문을 '결제 확인 중(PAYMENT_PENDING)' 상태로 두고 주문 확정을 대기한다. [E6] [E11]
- **사실** 알림 워커(notify)는 주문 완료 이벤트 수신 시 order의 상태 조회 API를 호출하여 주문 확정(CONFIRMED) 상태임을 확인한 후 알림을 발송한다. [E3]
- **사실** 주문 상태 조회가 타임아웃되거나 결제 확인 중인 경우 notify는 알림 발송을 보류하고 재시도 간격을 늘린다. [E4]
- **사실** 알림 처리 오류나 지연으로 인해 주문 상태를 변경하거나 결제를 취소하지 않으므로, ledger 지연이 notify에 의해 결제 취소로 이어지지 않는다. [E4]

### [E3] RUN-02:v1 §1 · approved
원문: data/raw/RUN-02_v1.md

알림 워커(notify)는 주문 완료 이벤트를 받으면 주문 서비스(order)의 상태 조회 API를 호출한다. 호출 경로는 GET /v1/orders/{order_id}/status다. 조회 결과가 주문 확정(CONFIRMED)이면 알림을 발송한다.

이벤트를 받은 시점과 실제 주문 상태가 다를 수 있어 발송 직전에 상태를 다시 확인한다. 같은 이벤트가 여러 번 들어와도 주문 번호(order_id)와 알림 종류(notification_type)가 같으면 한 번만 발송한다.

### [E4] RUN-02:v1 §2 · approved
원문: data/raw/RUN-02_v1.md

주문 상태 조회가 타임아웃되면 알림을 보류하고 재시도 간격을 점차 늘린다. 결제 확인 중인 주문도 확정 상태가 확인된 뒤 발송한다. 알림 처리 오류로 주문 상태를 변경하거나 결제를 취소하지 않는다.

알림 지연 문의가 들어오면 큐 대기 건수, 가장 오래 대기한 건의 시간, 주문 상태 조회 오류를 확인한다. 결제·원장 장애가 함께 발생했다면 주문 확정이 늦어진 것인지, 확정 이후 알림만 늦어진 것인지 주문 번호로 확인한다.

### [E6] ADR-07:v1 §1 · approved
원문: data/raw/ADR-07_v1.md

주문 서비스(order)는 결제 서비스(pay)를 동기로 호출하고, 결제 완료 응답을 받은 후 주문을 확정한다. 출고 시스템에는 확정된 주문(CONFIRMED)만 전달한다.

결제 응답이 오지 않으면 주문을 ‘결제 확인 중’(PAYMENT_PENDING)으로 두고 기존 결제 건의 처리 결과를 확인한다. 구매 화면에도 ‘결제 확인 중’을 표시한다. 상태가 확인될 때까지 같은 주문으로 결제를 다시 요청하지 않는다.

### [E8] ADR-07:v1 §3 · approved
원문: data/raw/ADR-07_v1.md

PG 승인은 완료됐지만 원장 기록이 끝나지 않은 결제는 ‘원장 반영 대기’(LEDGER_PENDING)로 저장하고 대사 큐에 넣는다. 대사 작업은 PG 승인 내역과 원장 기록을 비교한 뒤 기존 결제 ID(payment_id)로 처리한다. 장애 시 큐 중지와 재개는 OPS-04 v1을 따른다.

비동기 결제 방식은 결제 내역 대사와 출고 취소 처리를 자동화한 후 다시 검토한다. 결제정산팀은 중복 승인·원장 누락 처리 방안을, 커머스플랫폼팀은 출고 단계별 취소 가능 범위를 정리한다.

### [E11] ARCH-01:v1 §2 · approved
원문: data/raw/ARCH-01_v1.md

결제 서비스(pay)는 PG사의 승인 응답을 받은 뒤 원장 서비스(ledger)의 POST /v1/journal-entries를 동기로 호출한다. 결제 ID(payment_id), 가맹점 ID(merchant_id), 금액, 통화, 승인 번호를 원장에 기록한다.

중복 기록은 결제 ID와 전표 유형(entry_type)의 조합으로 확인한다. 같은 요청이 다시 들어오면 기존 처리 결과를 반환한다. 결제 ID와 전표 유형이 같은데 금액이 다르면 오류로 처리한다.

| 호출 구간 | API | 타임아웃 | 타임아웃 시 처리 |
| --- | --- | --- | --- |
| 쇼핑몰 → 주문 | POST /v1/orders | 5초 | 기존 주문 번호로 상태 조회 |
| 주문 → 결제 | POST /v1/payments/authorize | 3초 | 결제 확인 중(PAYMENT_PENDING)으로 유지 |
| 결제 → 원장 | POST /v1/journal-entries | 1.8초 | 원장 반영 대기(LEDGER_PENDING)로 저장 후 대사 큐에 등록 |

응답을 받지 못했더라도 PG사에서 이미 승인했을 수 있다. 결제를 새로 요청하기 전에 기존 결제 ID로 승인 내역을 조회한다. 각 서비스에서 독립적으로 자동 재시도하지 않고, 결제 서비스에서 확인과 재처리를 담당한다.
