6교시 실습 A: 구조 질의 결과를 출발점으로 원문에서 설명 근거를 찾아라.

질문: ledger 지연 시 점검 후보를 이해하려면 어떤 설계 이유, 운영 조치 조건, 과거 관측의 맥락을 확인해야 하는가?

입력
- input.json: 실제 구조 질의에서 얻은 스냅샷, 점검 후보, 초기 문서 ID, 후보별 문서 연결(candidate_doc), 규칙과 사실 ID 경로다. candidate_doc의 각 행은 [서비스 ID, 문서 ID]이다.
- raw/*.md: 후보의 업무 영향과 조치 판단에 필요한 근거를 찾을 문서 원문이다.
실행 스크립트가 각 파일의 내용을 참고 파일(JSON)의 file/content로 제공한다. 제공된 내용 안에서 탐색하고 외부 검색이나 파일 접근 도구를 호출하지 마라.

근거 탐색 절차
1. input.json에서 snapshot_id, candidates, initial_doc_ids를 읽어 그대로 유지하라. 후보별 초기 about 연결은 candidate_doc에서 확인하라. 문서 본문에 서비스가 언급되는 것과 구조 질의에 about 연결이 적재된 것은 다르다. 초기 문서 연결이 없는 후보를 제거하거나 원문에 등장한다는 이유만으로 새 후보를 추가하지 마라. 구조적 점검 후보와 실제 장애 확정을 구분하라.
2. initial_doc_ids에 해당하는 문서의 번호·버전·상태·적용 대상을 확인하고 관련 절을 읽어라. 호출 관계와 상태 전이, 동기 처리에 관한 설계 결정과 그 이유를 찾아라. 문서가 최신이라는 이유만으로 질의에 사용한 운영 근거를 다른 설계안으로 대체하지 마라.
3. 초기 문서의 관련 문서·후속 작업·운영 절차 참조를 따라 질문에 필요한 추가 문서를 찾아라. 제공 원문에 실제로 포함되어 읽은 문서만 expanded_doc_ids에 기록하고 initial_doc_ids와 중복하지 마라. expansion_reason에는 어느 문서의 어떤 절을 통해 어떤 문서를 추가했는지와 추가 이유를 적어라. 참조 문서가 입력에 없으면 읽었다고 하지 말고 gaps에 남겨라.
4. 장애 기록에서 관측 대상과 집계 기준, 전체 건수와 영향 건수, 실제 증상, 대응 경과를 찾아라. 시간 수치마다 시작·종료 사건과 측정 대상을 확인하여 서로 다른 회복 단계를 구분하라. 과거 관측을 현재 사고의 지표나 향후 복구 보장으로 바꾸지 마라.
5. 운영 절차에서 조치 검토 조건, 확인할 자료, 대상 범위, 승인 주체, 중지·계속 운영·재개할 작업을 찾아라. 문서 자체의 승인과 개별 사고의 실행 승인을 구분하라. 조건부 절차를 무조건 실행하는 조치로 바꾸지 마라.
6. 설계 결정과 이유, 장애 규모와 시간의 의미, 조치 진입 조건과 승인, 실제 조치 범위를 각각 뒷받침하는 근거 항목을 수집하라. 각 항목의 quote는 해당 절에 실제로 존재하는 연속 문자열을 그대로 복사하라. 축약·생략 표시·문장 합성을 하지 마라.
7. explanation은 해당 항목의 quote가 직접 뒷받침하는 내용으로 한정하라. 다른 절의 수치·조건을 섞으려면 그 절을 인용하는 별도 항목을 만들어라. 경로를 결합한 영향 추론 등 원문 사실을 넘어서는 해석은 interpretation에 쓰고 단정하지 마라. 현재 상황에 적용하려면 추가로 확인해야 할 정보와 제공 자료의 공백을 gaps에 적어라. 현재 상황의 관측·실행 승인·복구 전망을 판단할 근거가 있는지도 각각 확인하라. 없는 근거나 실제 사람의 검토·승인 기록을 만들어내지 마라.

출력 스키마
evidence_bundle.json에 저장할 JSON 객체 하나만 출력하라. JSON 밖의 설명이나 코드 블록은 출력하지 마라.
- snapshot_id: input.json에서 읽은 스냅샷 ID
- candidates: input.json의 후보 서비스 ID 배열
- initial_doc_ids: input.json의 초기 문서 ID 배열
- expanded_doc_ids: 원문의 참조를 따라 추가로 읽은 문서의 "문서ID:버전" 배열
- expansion_reason: 출발 문서·절, 추가 문서와 이유를 설명하는 문자열
- items: 근거 항목 배열. 각 항목에는 아래 필드를 모두 포함한다.
  - service: 해당 근거와 관련 있는 candidates의 서비스 ID 하나
  - source_id, version: 원문에서 확인한 문서 번호와 버전을 별도 필드로 기록
  - section: 실제 근거 절을 "§번호" 형식으로 표기
  - quote: 그 절에 존재하며 해당 설명을 뒷받침하는 연속 인용문
  - evidence_kind: 근거의 종류를 나타내는 한국어 설명
  - explanation: 인용한 사실과 질문의 관련성을 설명하는 한국어 문장
  - interpretation: 원문 사실을 넘어서는 해석이 있으면 그 내용과 한계, 없으면 null
- gaps: 확인하지 못한 사항과 필요한 추가 증거를 적은 문자열 배열
- mode: "LLM 생성 초안; 원문 인용 자동 검사 후 사람 검토 필요"

제출 전 후보·초기 문서는 입력과 같은지, 추가 문서는 실제 참조로 연결되는지, 수치·절·인용·설명은 원문과 일치하는지 대조하라. 근거가 없으면 검증을 통과하기 위해 내용을 채우지 말고 gaps에 남겨라.
