원문과 추출 결과를 대조하여 review_suggestions.md에 저장할 Markdown 검토 제안서를 작성하라.
검토 대상 ID와 주장은 assertions.jsonl 및 error_candidates.json에서 직접 읽어라. 파일명이나 ID 접두사만으로 정답·오답·오류 종류를 미리 결정하지 마라. 각 ID별로 주장 / 권고 판정 / 원문 근거 / 수정 또는 보류 이유를 표로 정리하라.

모든 후보에 같은 기준을 적용하라.
- 원문 절에 정확한 연속 인용이 존재하며 주장 전체를 뒷받침하는가?
- 타입·표준 ID·별칭이 원문과 온톨로지 정의에 맞는가?
- 직접 HTTP 호출과 간접 경로, 호출 주체와 API 제공자, 운영 담당 팀을 구분했는가?
- 문서 버전·상태·업무 적용 범위·배포 여부를 확인하여 현재 운영 근거를 사용했는가?
- 제공 자료만으로 판단 가능한가, 추가 원문이나 검토가 필요한가?

권고 판정은 approved, rejected, held 중 하나로 원문 대조 결과에서 도출하라. 오류 예문도 왜 잘못됐는지를 원문으로 입증하고, 잘못된 주장은 수정할 내용과 근거를 설명하라. 오류 예문을 그대로 승인 사실 파일에 넣지 마라. 검토 중인 설계 변경은 현재 운영 사실과 분리하고 문서 상태를 표시하라.
aliases.json과 entities.json도 같은 기준으로 원문과 대조하고, 별칭 통합·서비스 ID 표기·타입·API·타임아웃·담당 팀의 불일치가 있으면 별도 절에 기록하라.
서비스 ID는 모든 결과에서 svc: 접두사 없이 통일한다. 별칭은 원문이 동일 서비스임을 명시한 이름으로 한정하고, 배포 리소스 이름이나 여러 이름의 나열 표기 전체를 서비스 별칭으로 임의 통합하지 마라.
원문 링크는 [문서 ID 버전 §절](raw/실제파일명.md)로 붙여라. 인용부호 안에는 해당 절에 존재하는 연속 문자열만 넣고, 요약과 추론은 구분하라.
문서 첫머리에 'LLM 검토 제안 — 사람 검토 전'을 표시하라. 권고를 사람의 실제 승인으로 표현하지 말고 review.csv, approved.jsonl을 수정하거나 검토자·검토 일자를 꾸며내지 마라. 제공된 항목을 빠짐없이 검토하되 100줄 이내로 작성하라.
